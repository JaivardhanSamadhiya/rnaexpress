# Owned Windows job utility — API and scope

`src/generalization_pum_resource_calibration_20261009/winjob.py` uses only Python standard-library modules and lazy Win64 `ctypes` bindings. Importing it does not load scientific packages, query resources, create a job, or start a process. Root owns the separate approval/freeze/controller and the actual two-PUM-phase launch. This utility does not replace any original resource callback or change any host/queue guard.

## Public interface

- `memory()` returns byte-valued `physical_available`, `physical_total`, `commit_headroom`, and `disk_available` for the project drive. Physical counters use `GlobalMemoryStatusEx`; commit headroom is `(GetPerformanceInfo.CommitLimit-CommitTotal)*PageSize`, not job-sensitive `ullAvailPageFile`. A failed query raises; there is no guessed fallback.
- `process_memory(process_handle)` returns `peak_working_set`, `working_set`, `peak_private_commit`, and `private_commit`. The peak private-commit field is Windows `PeakPagefileUsage`, while current private commit is `PrivateUsage`. These are commit counters, not an independently sampled resident-memory guarantee.
- `Job()` creates a new anonymous owned job and verifies exact process768 MiB, aggregate896 MiB, active-process2, and kill-on-close limits. No breakaway flags, parent-job modification, or compatibility fallback is enabled. Ancestor jobs may enforce stronger constraints.
- `Job.spawn(command: list[str], cwd: str)` requires an existing absolute executable and directory, quotes the list using Windows argument rules, and passes a mutable Unicode buffer to `CreateProcessW`. The flags are exactly `CREATE_SUSPENDED|CREATE_NO_WINDOW`, with no inherited handles and inherited environment. It attaches the suspended process, queries exact job limits and verifies membership before returning `Child`.
- `Child.pid`, `process_handle`, and `thread_handle` are the actual creation identities/handles. `Child.resume()` again verifies limits/membership and requires a previous suspend count of exactly1. A second resume is rejected. `exit_code()` returns `None` while running or the exact integer exit code after the process object is signaled; a legitimate259 exit code is preserved.
- `Job.limits()` returns `process_memory_limit`, `job_memory_limit`, `active_process_limit`, and `limit_flags`. `Job.accounting()` returns `peak_job_memory_used`, `peak_process_memory_used`, `active_processes`, `total_processes`, `terminated_processes`, `user_time_100ns`, and `kernel_time_100ns`.
- `Job.terminate()` / `Child.terminate()` terminate only this owned job. `Child.close()` closes the two creation handles; it does not substitute for closing the job. `Job.close()` closes its sole owned job handle and thereby kills remaining owned processes. Both close methods are idempotent. Use `finally` or the job context manager; no destructor is relied on for cleanup.

Create/assign/query/resume failures are fatal. An assignment failure explicitly terminates the newly created suspended process using its own creation handle, even if job assignment never succeeded. The utility never terminates a PID discovered by scanning unrelated processes. The monitoring controller remains responsible for startup/free-memory/commit/disk checks,100 ms observations, deadlines, immutable receipts and final post-hash policy checks. A signaled child and job active-process accounting can drain at slightly different instants; that does not widen the hard active2 limit.

If creation-failure cleanup itself fails, the raised error text includes the owned child PID and failed termination/wait/close operations. This remains a failed admission and possible suspended-process incident, never clean completion or permission for a different host/job fallback. The caller must preserve that diagnostic rather than automatically retry.

## Git helper routing and scoped tests

The first native invented-child test using the original `git` PATH resolution failed inside active2: `C:/Program Files/Git/cmd/git.exe` is a46,968-byte shim. Its failure is preserved in `winjob_tests_initial_git_incident.json`; the cap was not raised. A second preparatory run established that the direct Git helper succeeds; an instantaneous accounting-zero test assumption was then replaced with a bounded2-second drain check. This is synthetic lifecycle synchronization, not a scientific/resource tolerance change.

Root must pin and prepend `C:/Program Files/Git/mingw64/bin` in the controller/worker-private environment if using this route. Its `git.exe` is4,149,624 bytes with SHA256 `51c6331aab2426ae2df187975590587b5a10042e3423f4bc0fdcb54aeb3efab7`. The original scientific `subprocess(['git','show',...])` remains unchanged. No global PATH setting or Git installation is modified by the utility. The native source-helper test verifies the resolved direct helper and exact `git show HEAD:src/generalization_pum2_fixed_math_20261008/model.py` source hash within active2. This is not network publication or biological-data access.

`winjob_tests.py` contains mocked allocation/query/assignment/membership/resume/cleanup failures and exact Win64 layouts, plus three opt-in tiny native-child checks: local Python sleep/exit and post-exit memory; kill-on-close; and the source-only Git helper. Native tests require `PUM_WINJOB_NATIVE_TESTS=1`, the pinned direct-Git PATH, and fresh approved startup headroom; otherwise they are skipped/rejected, not counted as native admission. They never call either PUM producer or load a project sequence, phenotype, feature array or model.

## Primary API references

The native signatures, mutable command buffer and creation-handle ownership follow [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw). Assignment, membership and suspend-count checks follow [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [IsProcessInJob](https://learn.microsoft.com/en-us/windows/win32/api/jobapi/nf-jobapi-isprocessinjob), and [ResumeThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread).

Commit and resident fields follow [MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex), [PERFORMANCE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information), and [PROCESS_MEMORY_COUNTERS_EX](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex). Hard process/job memory limits and their peaks follow [JOBOBJECT_EXTENDED_LIMIT_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information). Ownership, child inheritance and kill-on-close follow [Job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). These mechanisms bound owned commit allocations; they do not eliminate transient physical-memory pressure or UI-disruption risk.
