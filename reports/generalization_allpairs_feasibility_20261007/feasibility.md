# Exact-pair risk feasibility, source-only

Pair coverage is an already attempted project question. The current cap256 sampler is a valid deterministic label-blind uniform sample of unique unordered pairs; omitting many candidates in a large menu is a finite sampling limitation, not a demonstrated software error. Increasing within-parent pair coverage adds no independent biological units or new labels. A bounded source/history scan finds a narrower controlled comparison not yet implemented: exact all non-tied large-menu logistic risk, with **both arms retaining the original cap256 source RMS, supported columns and context loss mass**. This is a subsequent exposed-data hypothesis, not a novel ranking method or assured generalization improvement.

Historical source findings:

* `cross_assay_20260927/models.py:pair_indices` enumerates all unordered pairs only when n(n−1)/2<=256 (n<=23). Larger menus use256 unique unordered edges selected before labels; exact truth ties are removed afterward. Each retained context gets mass1/(study count×components per study×contexts per component), divided equally among its surviving edges, followed by global normalization.
* `probabilistic_ranking_20260928/prepare.py` preserves this same cap256 roster. Pairwise calibration, candidate expected-win evaluation and complete ordering diagnostics do not constitute complete-pair training.
* `generalization_20261007/route_coverage.py` already forms a Hamiltonian candidate chain and fills up to min(all,max2048,n−1) edges. This gives complete *pre-tie candidate coverage* in large menus, and complete pairs for modest menus, but not every pair in larger menus. It also recomputes pair RMS from its expanded roster and includes a separate robust-loss variant. Therefore it does not isolate complete finite-menu risk with shared old scaling.
* V4's `_pairwise_training_data` iterates a utility-ordered directed roster up to2048 sampled training examples; its features/scaler, decision-set normalization, context residuals and weighting differ. `mechanism_v2/ranking.py` has its own128-pair cap. FinalShot's percentile/pointwise or decision objectives use candidate information differently. The bounded scan is not an exhaustive proof that every historical branch lacks an equivalent objective.

For transformed candidate rows z_i and u_i=z_iᵀβ, an eligible unordered pair i<j has t_ij=sign(y_i−y_j), exact truth ties omitted. With fixed context loss mass M_c and K_c non-tied pairs, its weight is M_c/K_c. Risk is Σ_c Σ_ij (M_c/K_c)log(1+exp(−t_ij(u_i−u_j))) + λ||β||²/2. Pair residual r_ij=−(M_c/K_c)t_ij sigmoid(−t_ij(u_i−u_j)); add r_ij to candidate gradient g_i and subtract it from g_j. Then ∇β=zᵀg+λβ. Within every context Σ_i g_i=0, so parent-constant shifts and the chosen feature mean cancel. This is the same exact finite-pair objective as constructing all feature differences, without an O(number of pairs×features) matrix.

Computationally, calculate candidate utilities once, stream upper-triangular utility/label comparison blocks (fixed proposed rowblock128), accumulate per-candidate residuals, then multiply the candidate feature matrix once. Complexity per optimizer evaluation is O(Σ_c n_c²+Np), plus transient O(128×largest menu) rather than pair×p. Counting exact non-tied pairs is n(n−1)/2−Σ_v count(y=v)(count(y=v)−1)/2; signed zero ties and all equal labels obey the existing equality convention. Use relational label comparisons rather than subtracting extremes, stable logaddexp/expit, deterministic original row/context order, one numerical thread and unchanged fixed L-BFGS/L2/selection rules. Actual time, maximum menu size, native block implementation and optimizer replay are unbenchmarked; the stdlib reference here is invented-example mathematics only, not a production implementation or fit.

Required matched-control constraints before any experiment:

1. Derive the old cap roster from each permitted training split only. Retain exactly its cap-positive contexts and their **sum of already normalized old edge weights**. Do not revive a context omitted because every sampled edge was an exact truth tie: that would also change training-context mass. Report such contexts if present. Include every candidate of each retained context in the all-pair objective; targets/full menus stay unchanged.
2. Compute cap256 training pair RMS once; use identical mean, RMS, threshold1e−8 and frozen unsupportedβ0 in both arms. Do not switch to all-pair RMS or admit new unsupported columns while claiming a pair-only comparison. This intentionally cannot recover a feature unsupported in the cap roster.
3. Both arms use identical fixed feature blocks, outcome orientation, original allele/component purges, source-only nested configuration selection, L2 [.005,.05,.5], biological hierarchy and canonical target exact-tie choices. No hard-pair mining, truth-extreme weighting, source-cohort pruning, noise reinterpretation, new calibration or target selection is included.
4. Numerical production code must independently compare loss/gradient to the old materialized capped objective on invented data and then retain the same numerical solver checks. A new preparation/prefit/creation-time checkpoint chain, full inner replay, complete original target menus and fixed information/gate controls remain mandatory. Old models cannot be silently reused as new solver controls without a separate exact provenance/identity certificate.

The pure stdlib tests verify direct pair-feature versus candidate-residual gradients, finite differences, unequal context masses, exact ties/signed zeros, capped-empty context retention, exhaustive small-menu equivalence, shared capped support, parent shifts, sign reversal and stable extreme margins. No actual project sequences, labels, feature matrices, checkpoints, numerical packages or optimizer calls are accessed. There is no production entrypoint, automatic search or fitting authorization.

More pairs might reduce finite-sampling variation while also giving correlated/noisy measured rankings more influence. They cannot fix missing cell state, absent sequence information, label/endpoint mismatch, reporter-context uncertainty or source novelty. Existing richer connected coverage failures therefore lower confidence but do not by themselves answer this tightly matched exact-risk comparison. Logistic pairwise ranking is established prior methodology; see the [primary RankNet paper](https://www.microsoft.com/en-us/research/publication/learning-to-rank-using-gradient-descent/). The residual-gradient identity above is ordinary differentiation, not a new method claim.
