It does not admit data, import a scientific runtime, read project inputs, bootstrap packages, sample pairs, expose a CLI or choose a new model/gate. Native or project execution requires a separate reviewed root controller.

The runner exclusively creates the new run container; an existing path is rejected untouched. The unchanged writer_v2.Campaign exclusively creates its checkpoints/ child. This separation permits exclusive runner_failure.json evidence for startup, campaign-constructor, selection, hook and write failures without contaminating the writer's exact successful63-trio directory roster. Every failure poisons the Campaign object if created and permanently consumes the new run path. Failure-evidence write errors are attached to the original exception; no overwrite, retry, resume or cleanup is attempted.

Follow the exact existing task_roster order: three arms, each three outer folds, each two inner folds times three configurations followed by its one chosen outer checkpoint. Call the original3GiB RAM/1GiB disk/one-thread gate at start and before each checkpoint, including after potentially slow integrity/selection work. The mandatory hook is called once before each attempted checkpoint with keyword task_key, deep-copied task, plan, prepared and campaign. It must return the Python singleton True after the future controller checks actual runtime/input/source integrity. An arbitrary callable's assertion is not an independently certified origin. Construct the original fit callback only after the first successful hook/resource checks; its existing fresh probe and immutable-pool validation before every actual minimize invocation remain unchanged.

Hook, selector, orchestration or writer errors stop immediately; no later checkpoint or known-failed finish is attempted. There is no extra runner success-file write after Campaign.finish: return its exact lifecycle-only result immediately. If the writer's finish itself partially writes and fails, retain that partial artifact and runner failure evidence; it is not a successful completion. Successful lifecycle status still explicitly leaves all63 independent numerical, source-only selection, prediction and gate checks pending. It cannot establish generalization or a biological result.

Preparation tests use invented plans, small callback/campaign stubs and exclusive temporary files only. They check exact order/count, six-inner prerequisites, failure poisoning, no outer fit after failed selection, no runtime callback after bad integrity/low RAM and non-resume.
